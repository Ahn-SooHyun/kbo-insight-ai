## 1. 목적·지원 범위

선수의 출전량과 누적 기록을 함께 예측하는 지도학습 다중 출력 회귀 문제다. 타자와 투수는 기록 정의가 다르므로 역할별 주 예측기 하나씩, 총 두 개를 목표로 한다. 여러 기간·기록은 공동 회귀 트리의 분기 구조와 잎 벡터를 공유한다. 기준 통계와 잔차 트리는 하나의 운영 예측 계산을 구성한다. 개발 중 비교 후보는 운영 모델로 저장하지 않는다. 실제 두 역할의 학습·선정·검증이 완료되면 기존 주 예측기 네 개와 합쳐 총 여섯 개가 된다.

예측 대상은 기준 월요일 이전에 같은 시즌의 관측 기록이 있는 선수·역할이다. 정규시즌 경기만 대상이며 포스트시즌, 공식 등록 명단 전체, 미래 이적, 비공개 부상 및 감독 의도는 추정하지 않는다. 정규시즌이 종료된 기준 시점은 지원 대상 밖이다. 시즌 전망은 현재까지 확인된 누적과 잔여 예측을 합산해 산출한다.

## 3. 입력·전처리

기준은 월요일 00:00 KST이며 당일 기록을 모두 제외한다. `sample_id`, `player_id`, `role`, `season`, `sample_date`, `last_observed_date`로 대상과 시점을 검증한다. `days_since_observed`는 날짜 차이와 일치해야 한다. `known_team_id`, `prior_rejected`, 역할별 `season_*`, `recent28_*`를 검증한다. `season_active=true`는 호출자의 정규시즌 진행 확인이다. 독립 추론은 호출자가 제공한 기록이나 증거의 진위를 외부 원천에서 인증하지 않는다.

트리 입력은 고정 달력 기준인 3월 1일 이후 경과일(최소 1일), 마지막 관측 경과일, 제외 이력 수, 팀 식별 불명 표지, 시즌 및 최근 28일 기록의 달력 일수당 관측량이다. 시즌 기록 환산 분모는 경과일과 28일 중 큰 값이다. 이는 실제 개막일이나 경기 수가 아니다. 미관측 수치에는 비음수 특징과 구별되는 -1 표지를 사용한다. 선수 ID 및 실제 팀 ID 자체, 미래 팀, 실제 미래 출전량, 미래 시즌 종료일, 정답·품질 사후 정보는 트리 특징으로 쓰지 않는다.

입력 계약은 최근 기록이 시즌 누적을 초과하는지, 날짜·식별자·기록 구성 및 허용 필드를 검사한다. 현재 누적은 `current_counts`, `current_scope`, `current_as_of`로 별도 제공할 수 있다. `current_scope=caller_verified`는 호출자가 동일 선수·역할·기간·기록 정의의 누적을 확인한 경우에만 사용하며 `current_as_of`는 기준 월요일(종료 제외 경계)과 같아야 한다. 별도 누적 없이 시즌 관측 Count 전체가 있으면 `observed_pbp`로만 제공한다. 기록 누락 시 최종 전망은 unavailable이다.

사전 확인된 정규시즌 종료 경계가 있는 별도 시나리오는 `known_end_exclusive`, `known_end_as_of`, `known_end_source`를 함께 제공한다. 증거 날짜는 기준 월요일보다 앞서고 종료 제외 경계는 기준일 이후여야 한다. 실제 역사적 종료 정답을 이 필드에 넣어 개발 성능을 높이지 않는다. 이 별도 시나리오의 구간은 보정되지 않았으므로 제공하지 않는다.

## 4. 정답·출력 계약

| 역할 | 기간별 Count                                                          | 공동 출력 차원 |
| ---- | --------------------------------------------------------------------- | -------------: |
| 타자 | games, pa, ab, hits, home_runs, walks, hbp, strikeouts                |             24 |
| 투수 | games, bf, outs, pitches, ab, hits, home_runs, walks, hbp, strikeouts |             30 |

기간은 `[t,t+7일)`, `[t,t+28일)`, `t`부터 정규시즌 공식 종료일 포함까지다. 종료일은 DB에서 종료 제외 경계로 표현한다. 고정 기간에 시즌 종료 이후 날짜가 있더라도 포스트시즌을 포함하지 않는다.

`usable`, `status`, `window_start`, `window_end`, `observed_through_exclusive`, `ready_date`, 기록별 NULL을 확인한다. `valid_observed` 및 `zero_observed`인 완전한 정답만 논리적 시점과 분할 경계에 맞을 때 사용한다. 실제 0과 부분 관측·미관측을 구분한다. `observed_*`를 완전 정답 대체값으로 사용하지 않는다. 동일 선수·역할에서 여러 기간의 유효 정답을 연결하며, 시즌 종료로 포함 범위가 동일한 정답은 같은 Count이어야 한다.

출력은 비음수 실수 기대 Count이다. 표시용 정수 반올림으로 구성 관계를 깨지 않는다. PA/BF, AB, BB, HBP, H, HR, SO의 구성 관계와 7일 ≤ 28일 ≤ 잔여 정규시즌 Count를 확인한다. 아웃과 투구 수는 주루 사건·무투구 타석 때문에 단순 상대 타자 수 상하한을 가정하지 않는다. 예측 단계에서 사전 확인한 종료일이 없는 경우 실제 사후 종료일을 사용하지 않고, 실제 종료로 범위가 같아진 표본의 예측 차이는 평가 진단에 남긴다.

`hit_rate=hits/ab`, `strikeout_rate=strikeouts/pa`(타자) 또는 `/bf`(투수)로 계산한다. 분모가 0이면 null과 `zero_denominator`를 반환한다. 투구 이닝은 `outs/3`의 실수이며 야구식 .1/.2 아웃 표기가 아니다. ERA, SLG, OPS 등 현재 정의와 구성 기록이 불충분한 통계는 지원하지 않는다. 시즌 전망은 현재 누적과 잔여 Count를 먼저 합산하고 비율을 새로 계산한다. 관측 PBP 누적을 사용한 시즌 전망은 공식 시즌 최종 성적이 아닌 잠정 관측 기준 전망으로 표시한다.

## 5. 모델·학습·선정

### 5.1 기준 모델

Train의 유효 7일 Count에서 달력 일수당 역할 평균을 계산한다. 개인 시즌 기록의 일수당 집계와 최근 28일 기록의 일수당 집계를 각각 장기·단기 기록률로 사용한다. 시즌 기록이 없으면 Train 평균, 최근 기록이 없으면 장기 기록률로 후퇴한다. 단기 0.7, 장기 0.3을 결합한다. 잔여 기간은 학습 시즌의 검증된 종료 제외 경계와 고정 3월 1일 기준 사이의 평균 경과일을 사용해 추정하며 최소 7일을 유지한다. 고정 기간의 기준 예측 환산 일수는 이 예상 잔여 기간과 7일·28일 중 작은 값이다. 이는 실제 미래 시즌 종료를 안다는 의미가 아니다.

### 5.2 공동 잔차 회귀 트리

공동 출력마다 Train 평균 Count와 1 중 큰 값을 척도 `s_j`로 계산한다. 기준 예측 `b_ij`와 관측 정답 `y_ij`의 정규화 잔차 `r_ij=(y_ij-b_ij)/s_j`를 사용한다. 각 기록의 유효 정답 마스크는 해당 출력의 학습과 분기 손실에만 적용한다. 미관측 출력을 0으로 채우지 않는다.

하나의 트리가 모든 기록의 분기를 공유한다. 각 출력의 전체 Train 관측 수 역수를 분기 손실 가중치로 사용한다. 양쪽 자식 노드에서 지원되는 기록의 잔차 제곱오차 감소를 합산해 공통 분기를 선택한다. 분기 후보는 Train 특징 분위수 20·40·60·80%로 한정한다. 최소 리프 행 수 40, 출력별 최소 자식 지원 8, 최소 이득 1e-12, 상위 노드 수축 상수 10을 적용한다. 지원 부족 출력은 상위 노드 예측을 사용한다. 최대 깊이 2와 4를 비교한다. Train 기준값과 한 트리의 잔차 벡터를 합한 뒤 비음수·구성 관계를 보존하는 기간별 증가량 후처리를 적용한다. 이는 엄밀한 확률 분포 적합이나 독립 기록별 회귀기의 묶음이 아니다.

### 5.3 시간순 개발 및 예측 구간

2024-01-01 이전에 정답이 완료된 2023 표본에서 선행 모델을 학습한다. 2024년 기준 표본 중 2025-01-01까지 관측이 완료된 유효 기록에서 절대 잔차를 계산한다. 기록별 90% 목표 구간 반경은 정렬 잔차의 `min(n,ceil((n+1)*0.90))`번째 값이다. 최소 20행, 서로 다른 선수 5명 및 기준 주 3개를 충족하지 못하면 지원 부족으로 null을 반환한다. 구간은 `[max(0,point-radius),point+radius]`로 표시한다. 시즌 전망 구간은 현재 누적을 같은 단위로 더한다. 현재 누적의 자체 측정 불확실성은 반영하지 않는다.

최종 후보는 2023~2024 Train 전체로 재적합하고 2024년 시간순 잔차 반경을 전이한다. 2025 Validation에서 후보를 평가한다. 두 트리 후보 중 기록별 정규화 MAE의 산술 평균, 정규화 RMSE, 깊이 순으로 선택한다. 기준 모델은 비교용이다. 선택된 후보가 기준보다 나쁘면 이를 명시하고 하위 검토에서 수용 여부를 판단한다. 2025년은 선정에 사용했으므로 독립 최종 평가가 아니다. 실제 운영 모델에 대한 90% 포함 보장은 없으며 동일 선수·중첩 기간의 의존성과 재적합 전이를 해석에 반영한다.

## 6. 강의 원리 및 프로젝트 확장

아래 강의 근거는 [개발 흐름의 선행 전사 확인 기록](../planning/development_workflow.md#lecture-methods)을 계승한다. 이번 Work에서 전사 원문 전체와 영상·슬라이드를 독립 재확인하지 않았다. 과제 안내 `창문해_TermProject_가이드.pdf`의 3·4·10페이지는 별도 확인했으며 강의 전사와 구별한다. 코드는 적용 제안 상태로 실제 실행 여부와 채택 결과는 후속 검증으로 갱신한다.

## 7. 평가 지표·실제 결과

기록·기간별 `MAE=mean(abs(y-p))`, `RMSE=sqrt(mean((y-p)^2))`, 평균 편향, 실제 평균과 유효 행·선수·기준 주 수를 계산한다. 정규화 MAE/RMSE는 Train 평균 기반 척도에서 비교한다. 각 후보의 Count 평가 표본과 마스크 수가 일치하는지 검사한다. 시즌·기준 주·사전 알려진 팀별 정규화 오차와 관측 위험은 행 또는 기록 셀 수를 독립 관측 수와 구별하여 해석한다.

구간 지표는 목표 포함 수준, 실제 포함 건수/유효 구간 건수, 평균 폭, 구간 미지원 건수다. 2024년 구간 적합 표본의 포함률은 적합에 사용한 자료의 진단이며 2025년 적용 포함률과 다르다. 예측 구간은 주변 Count에 한정하고 기록 간 동시 포함이나 비율 구간을 제공하지 않는다.

비율은 실제 분모 양수·정답 유효 행과 예측 분모 양수 행을 구분한다. 실제·예측 분모 합, 평가 가능 건수, 계산 불가 건수와 MAE를 보고한다. 7일은 유효 Count에서 재계산한 진단값이며 별도 수집·검증된 비율 정답이 아니다. 28일·잔여는 저장 비율과 해당 분모를 대조한다. 후보별 예측 분모 0 때문에 실제 평가 행이 달라진 경우 비율 MAE만으로 우열을 단정하지 않는다.

| 결과                                      | 현재 상태           |
| ----------------------------------------- | ------------------- |
| 실제 타자 학습·평가                       | 미실행              |
| 실제 투수 학습·평가                       | 미실행              |
| 기록별 마스크, MAE/RMSE 및 기준 대비 개선 | 미확인              |
| 90% 목표 구간의 2025 포함률·폭            | 미확인              |
| 선정 깊이 및 운영 자산 지문               | 미확인              |
| 별도 프로세스 재현                        | 미확인              |
| 최종 Test                                 | 미실행 및 격리 대상 |

실행 후 `evaluation.json`의 `data_audit`, `development.early_train_audit`, `development.calibration_audit`, `development.candidates.*.validation`, `development.candidates.*.validation_vs_baseline`, `development.record_scales`에서 근거를 확인한다. 실측 수치와 실행 ID는 사용자가 적용·실행한 로그 및 산출물을 확인한 뒤 이 문서에 갱신한다.

## 8. 구현·산출물·재현성

| 파일                                          | 책임                                         |
| --------------------------------------------- | -------------------------------------------- |
| `src/models/player_performance/__init__.py`   | 모델 버전·스키마                             |
| `src/models/player_performance/data.py`       | 읽기 전용 인수·입력·정답 마스크·품질 검사    |
| `src/models/player_performance/model.py`      | 기준 통계·공동 트리·제약·파생 비율·시즌 전망 |
| `src/models/player_performance/evaluation.py` | 시간순 적합·선정·Count/비율/구간 평가        |
| `src/models/player_performance/__main__.py`   | 학습·저장·검사·추론·독립 비교 CLI            |
| `tests/models/test_player_performance.py`     | 합성 단위·경계·통합 검사                     |

Python 3.12와 기존 프로젝트 설정을 사용한다. 신규 외부 실행 의존성·GPU는 필요하지 않다. 난수 없는 결정적 트리이며 프로젝트 Seed를 기록한다. 비교 후보와 운영 모델을 구분하고 각 역할은 별도 신규 실행 ID로 저장한다. 기존 산출물을 덮어쓰지 않는다. `models/m3/<실행ID>/model.json`에는 선택된 트리 하나, 기준 통계, 입력·출력 사전, 구간 반경, 설정 및 자료·코드 지문을 저장한다. `results/m3/<실행ID>/evaluation.json`, `example_input.json`, `example_prediction.json`, `manifest.json`에는 평가·재현 증거를 저장한다. 완료 매니페스트는 최종 저장 단계에서 작성한다. 원본 데이터·대용량 모델 자산·결과는 Git 추적 및 공개 재배포에서 제외한다.

저장 JSON의 구조와 내부 지문, 실제 파일 SHA-256, 모델·런타임 버전, 현재 실행 코드·설정 지문, 트리 분기와 출력 지지 수를 검사한다. `predict`는 모델 DB나 표준 DB를 열지 않고 저장 모델과 사전 입력 JSON만 이용한다. 동일 프로세스 저장 전후 비교 및 별도 프로세스 결과 지문 비교는 서로 다른 검증 단계다. 코드·설정 지문 변경, 자산 손상, 지원 외 역할·시점·기록 사전, 필수 증거 누락은 오류로 처리한다. 동일 환경의 정확 일치는 별도 재실행으로 확인하며 다른 OS에서의 실제 실행은 미확인이다.

## 9. 검증·한계·후속 연결

- 월요일 이전 기록·동일 역할·정답 완료·경계·실제 0·Null·비율 분모·기간과 구성 관계를 합성 테스트 및 실자료 감사로 구분해 검사한다.
- 실제 데이터의 Count 정의가 제안한 구성 검사와 충돌하면 오류를 숨기거나 원본을 수정하지 않고 근거를 확인한다. 현재 실자료 검사는 미실행이다.
- 선수 모집단의 공식 등록·이적·건강 상태 및 관측 기록의 전체 완전성은 보장하지 않는다. 2025년 투구 순번 누락과 28일·잔여 희소성으로 평가 표본이 선택될 수 있다.
- 달력 기준 및 과거 시즌 종료 평균은 단순 기준이며 실제 미래 일정·시즌 종료일을 아는 것으로 해석하지 않는다. 사전 확인한 종료 시나리오의 구간은 미지원이다.
- 기록별 기대 Count와 후처리는 선수의 실제 미래 개별 경기 경로나 인과 효과를 제공하지 않는다. 주변 구간에는 동시 포함 보장이 없고 겹친 창과 동일 선수는 독립 표본이 아니다.
- 기준 대비 성능 악화, 구간 지지 부족, 예측 분모 0, 실제 종료 동일 범위의 예측 차이는 모두 공개한다. 하위 수용과 최종 Test 검증 이전에 운영 성능을 확정하지 않는다.
- 기존 README 및 공통 예측·평가 계약의 구현·모델 수·성능 상태는 실제 결과가 확보된 뒤 업데이트한다. 기존 M1·M2·M4·M5 코드는 이번 제안에서 변경하지 않는다.

## 10. 실행 명령

저장소에 제안 코드 전체를 적용한 뒤 Windows PowerShell에서 실행한다. 각 학습 명령의 stdout은 결과 JSON이며 stderr는 로그다. 정상 종료 코드는 0이고 실패 시 후속 단계를 중단한다. 각 역할의 실행 ID와 자산 경로는 실제 stdout의 값을 사용한다.

```powershell
Set-Location -LiteralPath 'D:/Programming/kbo-insight-ai'
$kboPython = 'D:/Programming/kbo-insight-ai/.venv/Scripts/python.exe'
$dataRun = '259b38decaac4ed68dd5a596cfbe4849'

& $kboPython -X utf8 -B -m unittest tests.models.test_player_performance
if ($LASTEXITCODE -ne 0) { throw 'M3 tests failed' }
& $kboPython -X utf8 -B -m unittest discover -s tests
if ($LASTEXITCODE -ne 0) { throw 'Regression tests failed' }

foreach ($role in @('hitter', 'pitcher')) {
    $lines = & $kboPython -X utf8 -B -m src.models.player_performance train `
        --project-root (Get-Location).Path --data-run $dataRun --role $role
    if ($LASTEXITCODE -ne 0) { throw "M3 training failed: $role" }
    $summary = ($lines -join "`n") | ConvertFrom-Json
    $summary | ConvertTo-Json -Depth 10

    & $kboPython -X utf8 -B -m src.models.player_performance inspect --asset $summary.asset
    if ($LASTEXITCODE -ne 0) { throw 'Asset inspection failed' }

    $actual = Join-Path (Split-Path -Parent $summary.evaluation) `
        ("reloaded-" + [guid]::NewGuid().ToString('N') + '.json')
    & $kboPython -X utf8 -B -m src.models.player_performance predict `
        --asset $summary.asset --input $summary.input --output $actual
    if ($LASTEXITCODE -ne 0) { throw 'Independent inference failed' }

    & $kboPython -X utf8 -B -m src.models.player_performance compare `
        --expected $summary.expected --actual $actual
    if ($LASTEXITCODE -ne 0) { throw 'Independent comparison failed' }
}
```

정상 성공 조건은 두 역할의 학습 완료·각 운영 예측기 1개·최종 Test 미사용·자산 검사 및 재로딩 성공·전체 JSON 지문 일치다. 기준 대비 성능, 실제 포함률과 지지 부족은 성공 코드와 별도로 검토한다. 문제가 있으면 전체 오류 로그, 실행 ID, 실제 평가 파일과 테스트 종료 코드를 근거로 수정 필요 여부를 판단한다.
