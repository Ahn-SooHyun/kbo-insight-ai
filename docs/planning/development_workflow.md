## 1. 전체 흐름과 단계 경계

```text
설계·개발 기반
      ↓
자동 수집·표준화·입력/정답·시간 분할
      ↓
핵심 모델의 기준 비교·개선·보정
      ↓
시즌/포스트시즌·보조 기능 연결
      ↓
설정 확정·최종 평가·설명 종합
      ↓
재실행·운영 안내·최종 인수
```

개발 단계는 아래 기능별 작업으로 구성한다. 실제 착수는 요구 범위와 선행 검증 결과에 따르며, 계획 수립과 실행·검증 완료를 구분한다.

**부분 통합:** 개별 보조 기능은 필요한 모델이 준비된 범위에서 확인한다. 보조 기능·통합 전체 완료는 합의된 대상 기능의 연결을 모두 대조해야 한다. M1 후 시즌 전망의 조기 연결은 다음 예외 규칙을 따른다.

### 1.2 개발 순서의 예외와 반복

- M1이 검증되고 시즌 규칙·일정 입력이 확보되면 다른 모델 전체 완성을 기다리지 않고 시뮬레이션을 연결할 수 있다.
- 확률 보정·설명·오류 분석은 각 모델 개발 중 반복한다. 종합 검증 단계까지 미루지 않는다.
- 새 라인업·보조 입력으로 M1을 개선하면 같은 분할·지표로 다시 비교하고 관련 시뮬레이션·보고서를 갱신한다.
- 최종 Test는 이 반복 개선에 사용하지 않는다. [평가 계약](../standards/project_contract.md#evaluation)을 먼저 고정한다.

### 1.3 공통 기준의 관리 위치

| 기준                     | 상세 원문                                                       | 이 문서의 역할                    |
| ------------------------ | --------------------------------------------------------------- | --------------------------------- |
| 범위·시점·정답·누수 방지 | [예측·평가 계약](../standards/project_contract.md#information)  | 각 작업에서 확인할 입력·증거 연결 |
| 지표·기준 모델·Test      | [평가 기준](../standards/project_contract.md#evaluation)        | 개발·선택·최종 평가 순서 관리     |
| 원본·버전·경로·Secret    | [재현성 기준](../standards/project_contract.md#reproducibility) | 구현과 인수 책임 연결             |

상세 정의를 작업별로 복제하지 않는다. 규칙 변경 시 계약을 먼저 갱신하고 이 문서의 인수 조건·README 요약을 함께 대조한다.

## 2. 설계·개발 기반 준비

<a id="task-prediction-contract"></a>

### 예측·평가 기준 고정

**목적:** 수집 담당과 모델 담당이 같은 기능·시점·정답을 사용하게 한다.

| 구분         | 내용                                                                                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 입력         | 확정 기능 범위·기존 문서·사용 가능한 자료·실제 적용 위치                                                                          |
| 작업         | 동등 문서를 확인하고 [예측·평가 계약](../standards/project_contract.md)에 표본·입출력·기간·누수 방지·지표·기준 모델·미확정을 정리 |
| 산출물       | 단일 상세 계약, 문서 연결, 미확정 목록, 기준 대조 결과                                                                            |
| 완료 증거    | 기능별 시점·입력·출력·정답을 설명할 수 있고 미확정마다 책임·시점·확인 방법·사용 제한이 있음                                       |
| 실패 시 처리 | 실제 적용 위치·원본 가용성 미확인은 분리 기록. 원본 필드·기간·성능을 임의 확정하지 않음                                           |

상세 대조 항목은 [계약 검증표](../standards/project_contract.md#checks)를 사용한다.

<a id="task-development-foundation"></a>

### 최소 개발 기반

**목적:** 사업 기능을 선행 구현하지 않고 실제 설치·기본 실행·설정·경로를 검증한다.

| 구분         | 내용                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------- |
| 입력         | 실제 저장소·OS·설치 도구·기존 구조·계약의 저장/설정 책임                                  |
| 작업         | Python·환경/패키지 관리·최소 의존성을 근거로 선정·고정, 최소 패키징·진입점·설정·로그 구성 |
| 산출물       | 재현 가능한 환경 정의, 기본 확인 진입점, 경로·설정 안내, 의미 있는 최소 검증              |
| 완료 증거    | 실제 설치·import·기본 실행·설정 오류·경로 처리 결과와 실행 위치가 기록됨                  |
| 실패 시 처리 | 실행할 수 없는 기반을 완료 처리하지 않음. 실패 명령·환경·오류·보완·재검증 결과 기록       |

**확인할 경계**

- 프로젝트 기준 경로와 원본·중간·처리 자료·모델·결과·캐시의 책임을 구분한다. 정확한 물리 경로는 이 단계에서 정한다.
- 공백·한글 경로, 실행 위치, 대소문자 차이로 자료 위치가 달라지지 않게 확인한다.
- 도움말·기본 확인·import는 수집·학습·모델 로딩·대량 파일 생성을 일으키지 않는다.
- 실제 Secret은 추적·출력하지 않는다. 환경 파일 허용 범위는 계약의 [저장·설정 경계](../standards/project_contract.md#reproducibility)를 따른다.
- DB·Docker·CI/CD·GPU·서비스를 선제 도입하거나 미구현 수집/학습 명령을 성공처럼 반환하지 않는다.

## 3. 자동 수집·데이터 구축

<a id="task-source-pilot"></a>

### 소규모 확인과 조건부 판정

**목적:** 자료가 있다는 주장과 자동 처리 가능한 근거를 구분한다.

| 구분         | 내용                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| 입력         | 계약의 [확정 대기 목록](../standards/project_contract.md#decisions), 출처 후보·이용 조건 |
| 작업         | 소량 원본으로 필드·타입·식별자·순서·라인업·엔트리·교체·일정·경기 상태 연결 확인          |
| 산출물       | 원본 표본, 자동 확보 근거, 필드 의미 대응, 조건부 세부 항목의 잠정 판정                  |
| 완료 증거    | 실제 자동 확보 경로와 핵심 이벤트 대응을 설명할 수 있음                                  |
| 실패 시 처리 | 확보 실패·식별 불가·의미 불명을 구분. 수동 입력으로 통과시키지 않음                      |

**소규모에서 확인할 사례**

| 사례             | 확인할 질문                                               |
| ---------------- | --------------------------------------------------------- |
| 타석 중 교체     | 시작 참가자와 최종 결과 귀속을 구분할 수 있는가           |
| 주루로 이닝 종료 | 타석·투구와 별도 사건의 순서·아웃 변화를 연결할 수 있는가 |
| 무투구 타석      | 실제 투구 없이 끝난 결과를 투구 표본에서 분리할 수 있는가 |
| 라인업·일정      | 사건 날짜뿐 아니라 공개/수집 시각 근거가 있는가           |
| 좌표             | 단위·축·원점·결측·유도값의 의미를 확인할 수 있는가        |

대타·대주자·수비 교체, 도루·도루실패·견제사, 관측 번트 세부 항목은 각각 판정한다. 이 단계의 확인은 전체 자료 품질 통과가 아니며 표준화·품질 검사에서 재검증한다.

<a id="models"></a>

## 4. 핵심 예측 모델 개발

### 공통 개발 절차

```text
계약·가용성 확인 → 기준 모델 → 변수 비교 → 알고리즘 비교
              → 설정 최적화 → 시간 순서 검증·보정·오류 분석
```

문제별 점수의 우열을 비교하지 않는다. 각 문제 내부에서 같은 분할·표본·지표로 비교한다. 실험 후보와 최종 주 예측기, 전처리·보정의 학습 요소를 별도 기록한다.

**실행 인수:** 검증판을 읽기 전용으로 확인한 후 `python -m src.datasets.model_data`가 모델별 입력·정답·인덱스를 생성한다. 명시 분할은 2025-01-01(Validation), 2026-01-01(Test), 2026-11-26(관측 종료 배타 경계)이다. `train_eda.json`, `feature_target_contract.json`, `manifest.json`과 동일 입력 재생성 비교를 확인한다. 동일 경기와 M4 상태 쌍은 분할을 유지한다. M3는 월요일 이전 모집단과 정답 창·완료 시점으로 검사한다. 선수 과거 이력의 이름 충돌 최초 관측일과 최종 품질 판정을 분리하고 M2·M5·선발 과거 이력도 같은 절단을 적용한다. 정답 창의 팀·역할 품질 위험과 리그 관측 0 조건, 전체 M2 타석의 상태·제외 근거를 검증한다. 잔여 정규시즌의 완료 근거가 없는 과거 시즌을 학습 정답으로 확정하지 않는다. 관측 기록과 공식 기록을 구분하며 수정된 데이터 생성 판본으로 새 실행과 동일 판본 비교를 수행한다.

후속 핵심 모델은 **5개 기능군, 6개 주 예측기**(M1·M2·M4·M5 각 1개, M3 타자/투수 각 1개)를 사용한다. M5 위치와 별도 우승 전용 모델은 추가하지 않는다. 정규시즌 우승 및 한국시리즈 우승 전망은 후속 시뮬레이션에서 각각 제공한다. 시즌 공식 규칙·과거 일정 공개 시점·선수 이적/등록·예상 선발의 사후 정답과 당시 입력 경계를 분리하고, 지원되지 않는 정답이나 평가를 확정하지 않는다.

<a id="lecture-methods"></a>

### 강의 방법의 적용 기준

강의의 공통 원리는 기준 모델과 후보를 동일 표본에서 비교하고, 학습에 쓰지 않은 구간으로 일반화 성능을 확인하는 것이다. KBO 자료에서는 날짜 순서와 같은 경기 묶음을 유지한다. 각 Train에서만 학습형 전처리·특성 선택·분류기/회귀기 학습을 적합한다. 보정은 Train 내부의 적절한 예측 또는 별도 시간순 개발 구간에서 적합할 수 있으며, 보정에 쓴 표본과 후보 선정·최종 평가 표본을 구분한다. 무작위 K-fold·Stratified K-fold·OOB 결과는 최종 시간 순서 평가를 대체할 수 없다. 비교 후보의 채택은 검증 결과를 근거로 별도 결정한다.

비교 결과에는 데이터·코드 버전, 후보별 학습·검증 구간과 표본 수, 주 지표와 보조 지표, 보정 적합 구간, 오류 사례, 시간·메모리, 채택 여부와 이유를 남긴다. OOB는 랜덤 포레스트 후보를 실제 실험할 때 학습 구간 내부 진단으로만 참고할 수 있다. 소프트 보팅·스태킹은 단일 예측기가 검증 기준에 미달하고, 추가 예측기가 모델 수 한도와 시간 순서 조건을 충족한다는 근거가 확보될 때 검토한다. 스태킹의 상위 학습 입력은 해당 시점 이전 데이터로 만든 하위 예측으로 구성한다. OOB는 개별 학습 표본을 포함하지 않은 트리의 예측을 사용하는 내부 진단이며 날짜순 최종 검증을 대체하지 않는다. 단일 독립 모델의 계수 평균화와 여러 독립 예측기의 앙상블을 구분한다.

## 9. 증거·실패·변경 관리

### 9.1 상태를 구분하는 말

| 상태          | 뜻                                               |
| ------------- | ------------------------------------------------ |
| 설계          | 기준과 방법을 정했으나 적용·실행은 별도          |
| 적용          | 실제 파일·설정에 반영됨. 동작 성공을 뜻하지 않음 |
| 실행          | 특정 환경에서 수행함. 결과 검증을 뜻하지 않음    |
| 검증          | 기준·입력·실제 결과를 대조하고 근거를 남김       |
| 제한 / 미확인 | 범위가 좁거나 직접 확인할 수 없음                |

단계 완료는 파일 존재나 성공 메시지 하나로 판단하지 않는다. 요구사항·실제 적용·필요 실행·오류/한계·후속 인수가 모두 설명돼야 한다.

### 9.2 최소 증거 묶음

| 증거      | 기록할 내용                                      |
| --------- | ------------------------------------------------ |
| 기준      | 코드/문서·데이터·설정·분할 버전과 실제 작업 위치 |
| 실행      | 실행 식별자·실행 시각·환경·명령/설정·성공/실패   |
| 자료      | 출처·포함 기간·대상 목록·누락·정정·제외          |
| 결과      | 산출물 위치·요약·비교 대상·평가 지표·오류        |
| 확인 수준 | 직접 확인·전달받은 결과·미실행·미확인 구분       |

### 9.3 실패와 회귀 확인

실패하면 원인·영향 대상·사용 제한·보완 방법·재검증 결과를 남긴다. 단계의 공통 대응은 다음과 같다.

| 발견한 문제              | 즉시 제한                                      | 다시 확인할 근거              |
| ------------------------ | ---------------------------------------------- | ----------------------------- |
| 접근·원본·필드 의미 불명 | 해당 자료를 정상 입력으로 채택하지 않음        | 원본·조건·변경 이력·의미 대조 |
| 누수·정답·분할 오류      | 영향 평가 결과를 유효한 성능으로 유지하지 않음 | 경계·관측 완료·표본/경기 목록 |
| 모델 수·출력 가정 불일치 | 이름·파일 포장으로 숨기지 않음                 | 실제 학습 요소·대안·평가 영향 |
| 실행·경로·Secret 문제    | 성공 처리·민감 출력·임의 경로 생성을 막음      | 환경·설정·로그·오류 사례      |

원본 정정·분류 변경은 처리 자료와 정답·분할·모델·예측·평가의 영향 범위와 재생성 여부를 추적한다. 문서만 바뀌면 링크·기준 일치·누락을 대조하고 무관한 Unit Test를 만들지 않는다.

### 9.4 공통 문서 작성 및 검토 규격

문서는 저장소 사용자가 동일 기준으로 읽고 실제 실행을 재현할 수 있는 기술 계약으로 관리한다. 시각적 간결성을 이유로 정보 시점, 제외 사유, 모델 가정, 지표 분모, 검증 범위 또는 실패 처리를 생략하지 않는다. 제목과 표의 표현을 맞추되 문서의 역할에 맞는 상세 내용은 유지한다.

| 문서 종류       | 담당하는 내용                                                   | 원문 위치                                                                                                                                                                                                                     |
| --------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 프로젝트 진입점 | 현재 상태, 경로, 자료 계보, 설치·운영·장애 확인, 상세 문서 링크 | [README](../../README.md)                                                                                                                                                                                                     |
| 개발·인수       | 선후 관계, 단계별 검증과 의사결정, 강의 출처 및 공통 문서 규격  | 이 문서                                                                                                                                                                                                                       |
| 규범 계약       | 예측 시점·입출력·정답·분할·모델 수·품질·재현의 공통 경계        | [예측·평가 계약](../standards/project_contract.md)                                                                                                                                                                            |

**공통 형식:** 문서 제목, 한 줄 설명, 문서 역할·적용 범위·검토 기준일·저장소 경로·소스 기준, 관련 Issue(모델 문서), 관련 문서, 찾아보기, 번호 있는 절과 명확한 하위 제목을 사용한다. 상대 링크와 의미가 명확한 안정 앵커를 사용한다. 공개 기술 문서의 명칭은 실제 기능·작업·책임을 나타내며, 개인용 작업 추적 코드와 협업용 내부 식별자는 새로 사용하지 않는다. 같은 이름의 개념은 같은 뜻으로 사용하고 수치는 단위·분모·평가 날짜·실행 ID와 함께 기록한다.

**모델 실행 문서의 공통 10절 구조:**

| 절  | 제목                       | 필수 상세 내용                                                  |
| --- | -------------------------- | --------------------------------------------------------------- |
| 1   | 목적·지원 범위             | 예측 시점·문제 정의·대상·제외·운영 상태                         |

| 10  | 실행 명령                  | 확인된 환경에서의 신규 학습·저장 자산 재검증·추론·오류 처리     |

M1·M2·M3·M4·M5에 동일 적용한다. 기존 문서의 상세 정보와 호환 앵커를 보존하고, 개정할 때 아래 6절의 세부 구성을 맞춘다. 형식만 통일하기 위해 검증 완료한 모델 코드·지표·입력 범위를 변경하지 않는다.

| 6절 하위 제목                        | 필수 내용                                                                                                                                                             |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6.1 강의에서 확인한 원리의 실제 적용 | 전사에서 확인된 개념, 직접 구현 또는 문제에 맞춘 원리 활용 여부, 코드/수식 위치, 적용 이유, 운영·비교 실험 여부 및 실제 증거. 과제 안내 요구는 강의 내용과 별도 표시. |

| 6.3 주요 미적용 방법과 판단          | 실제 비교했으나 미채택한 기법과 전혀 실험하지 않은 기법을 분리하고 이유를 기록한다. 측정되지 않은 우열은 주장하지 않는다.                                             |
| 6.4 강의 및 이론 근거                | 파일명·전사 확인 시각·과제 가이드 쪽수·참고문헌 식별자·확인 범위·미확인을 연결한다.                                                                                   |

**고정 앵커와 표현:** 모델 문서의 대표 앵커는 `overview`, `data`, `inputs`, `outputs`, `method`, `lecture-methods`, `evaluation`, `reproducibility`, `limitations`, `commands`이다. 이미 링크된 이전 앵커는 호환 별칭으로 유지한다. 일반 문서는 역할에 맞는 기존 번호·앵커를 보존한다. 표는 Markdown 표로 통일하고 수치의 단위·분모·정밀도·방향을 명시한다. 코드 블록은 실제 언어와 확인 경로를 표시한다. 시각 장식보다 기술적 완전성·검증 가능성을 우선한다. 제목은 H1 한 개, 번호 절은 H2, 하위 절은 H3를 기본으로 하고 긴 수식·실제 실행 결과·클래스별 표는 필요한 상세 항목으로 유지한다. 장식용 색상·HTML 레이아웃으로 평가 상태를 표시하지 않고 문장과 표에 명시한다.

| 기록 유형        | 필요한 근거                                      | 작성 규칙                                                                                     |
| ---------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 직접 강의 적용   | 전사 파일명·시간 및 코드 위치                    | 강의에서 설명된 방법과 실제 구현의 대응을 구체화                                              |
| 원리 변형        | 강의 개념·문제 제약·변경 이유                    | K-fold의 공정 평가 원리를 시간순 분할로 적용하는 것처럼 동일 알고리즘 실행과 구분             |
| 과제 안내 적용   | 과제 가이드 요구 항목                            | 강의에서 직접 가르쳤다는 주장과 구분                                                          |
| 비교 실험·미채택 | 후보·동일 분모·설정·지표                         | 구현과 운영 선택을 분리, 악화 수치도 기록                                                     |
| 강의 외 확장     | 이론·참고문헌 또는 프로젝트 설계, 코드·검증·한계 | 확인한 강의 자료에서 동일 세부 기법을 찾지 못한 범위를 명시; 새 방법의 최적성을 가정하지 않음 |
| 미실험·미확인    | 범위 및 이유                                     | 미래 계획·제안은 실제 결과와 분리                                                             |

- 수식의 기호·단위·정답·입력 정의와 실제 구현 위치를 연결한다. 의사 표본·정규화·보정·하이퍼파라미터가 최적값이라는 근거가 없으면 사전 고정 설정 또는 제한 탐색으로 적는다.
- 현재 검증 자료와 과거 인수 자료의 실행 ID 및 상태를 구분한다. 사용자 전달 로그·직접 원격 확인·직접 재실행·원본 해시 직접 검증을 별도로 표시한다. 실행 결과 원본을 확인하지 못했으면 로그에서 확인한 수치로 한정한다. 학습 ID, 모델/평가 지문, 자료·소스 지문을 추적 가능하게 연결한다. 모델 후보·운영 모델·최종 Test의 역할을 구별한다. 지표 개선과 악화를 동시에 표시하며 미실행·미확인을 성공으로 바꾸지 않는다.
- 코드·설정·자료 버전·자산·실행 명령 변경 시 실제 적용·재실행 근거와 회귀 영향을 확인한다. 문서만 변경한 경우 코드 테스트 재실행을 했다고 쓰지 않는다. 기존 Issue/PR 템플릿의 필드와 규칙은 유지한다.
- 변경 후 문서 간 상호 링크, 기존 안정 앵커, 실제 경로·명령·수치·모델 개수의 일치, 코드 블록 닫힘 및 Git 공백을 검사한다. 자료 및 Secret을 문서·공유 저장소로 재배포하지 않는다. AI 활용 내역은 실제 활용·검토 수준을 사실대로 작성하고 팀의 최종 과제 보고서 기록을 별도로 유지한다.
