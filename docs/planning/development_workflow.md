### 1.2 개발 순서의 예외와 변경 통제

데이터 누락이나 원천 기록 충돌이 발견되면 임의 수동 정정 대신 자동 확인의 가능성과 품질 조건을 검토한다. 새로운 자료나 주 예측기, 배포·LLM 결합, 신규 규칙 적용은 별도 범위다. 한 작업에서 발생한 발견이 다음 작업을 변경할 필요가 있으면 의존성·원인·영향·완료 기준을 먼저 확정한다. 이미 공개된 Test를 보고 선정 기준을 변경하지 않는다.

### 1.3 공통 기준의 관리 위치

[공통 계약](../standards/project_contract.md)은 시점·정답·기능·모델 수·평가 원칙을 정의한다. 개별 모델의 실제 입력·알고리즘·파라미터·실험·오류·명령은 기능별 실행 계약에 남긴다. README는 사용자 진입점, [실행 인수](../standards/execution_handover.md)는 실제 환경과 저장 자산의 연결 책임을 가진다.

## 2. 설계·개발 기반 준비

<a id="task-prediction-contract"></a>

### 2.1 예측·평가 기준 고정

모델마다 표본 단위, 입력 시점, 미래 예측 대상, 정답 종료와 유효 분모를 먼저 정한다. 관측되지 않은 자료를 실제 0으로 가정하지 않는다. 원본에서 구별 가능한 세부 결과만 범주화한다. 공통 규칙의 변경은 영향 받는 자료·모델·평가·시즌·설명 계약에 연결한다.

<a id="task-development-foundation"></a>

### 2.2 최소 개발 기반

Python 3.12.15, uv 0.13.7, `.python-version`, `pyproject.toml`, `uv.lock`, `kbo.toml`을 기준으로 한다. 사용자 실행은 같은 가상환경의 Python을 명시한다. 설정·소스·테스트·문서와 생성 데이터/모델/결과는 경로 책임을 구분한다. Secret은 추적하지 않는다. 최소한의 표준 라이브러리 기반 모듈을 유지하고 데이터 검사에서 필요한 선택 의존성만 사용한다. GPU는 실질적 이득과 지원 근거가 있을 때만 추가한다. Notebook은 핵심 로직의 정본이 아니라 EDA와 실험·시각화에 사용한다.

완료 근거: 실제 두 CLI 진입점, 도움말·`check`, 설정 정상/오류 경계, 잠금 설치, 읽기 전용 동작, 테스트 로그와 결과 파일. [README 설치·실행](../../README.md#commands).

## 3. 자동 수집·데이터 구축

<a id="task-source-pilot"></a>

### 3.1 소규모 원천 확인과 조건부 판정

승인된 자동 수집 원천의 실제 바이트·필드·식별자·이벤트 순서·파일 형식·자료 이용 권한을 점검한다. Naver 표본과 고정 HF 배포 파일의 응답 제한·타입·구조·원본 재열람을 구분한다. 통신 성공은 의미 검증을 뜻하지 않으며, 표본의 필드 존재는 전체 자료의 완전성을 뜻하지 않는다. 라인업 발표 시각, 교체, 도루·견제·번트의 자동 식별 가능성을 항목별로 기록한다.

<a id="task-source-collection"></a>

### 3.2 전체 확보와 원본 보존

명세는 대상·판본·출처·조건을 고정한다. 재시도·timeout·응답 제한·실패와 보류를 기록한다. 저장 객체는 SHA-256으로 판별하고 기존 파일을 수정하지 않는다. 중단 뒤 재개는 이미 확보한 객체의 검증과 미완료 목록에 근거한다. 수집·갱신과 단순 보고는 별개 명령이다. 인수 원본 46개, 논리 대상 48개, 판본 50개는 실제 확인 기록의 범위다.

<a id="task-standardization"></a>

### 3.3 표준화·품질·집계 대조

raw → interim → processed의 변환 이력을 보존한다. 컬럼·타입·Null·범위·중복·식별자·날짜·경기·타석·투구 관계와 경기/선수별 집계를 확인한다. Raw와 기존 표준판은 수정하지 않는다. 보완 표준판에는 포스트시즌 유효 결과 46경기 및 정규시즌 종료 근거를 연결했다. #40에서 동일 입력으로 신규 보완판과 기존 DB 물리 해시 일치를 확인했다. 이 검증은 공식 모든 경기 기록의 사실 인증이 아니다.

<a id="task-model-data"></a>

### 3.4 모델 입력·정답·시간 분할

모델별 논리 표본을 만들고 같은 경기의 하위 기록을 중복·교차 분할하지 않는다. M3는 월요일 기준의 모든 과거 입력과 미래 기간 정답을 분리한다. 학습 시점에 관측이 완료된 정답만 사용하며 기간 중 실제 0과 미관측, 미완료, 0 분모를 구별한다. 입력·정답 허용 열, 감사 열, 데이터 분할·제외는 명세 및 검증 결과에 남긴다. Train EDA는 Train 기준의 특성·지원·누락·기준 통계에 사용한다.

| 구간       | 기간(논리 시각 KST)             | 역할                             |
| ---------- | ------------------------------- | -------------------------------- |
| Train      | 2025-01-01 이전                 | 기준·학습·학습형 전처리          |
| Validation | 2025년                          | 개발 비교·선정, 모델별 보정 분리 |
| 최종 Test  | 2026-01-01 이상 2026-11-26 미만 | 고정 모델 독립 평가만            |

자료 범위와 실제 완료 정답은 모델별로 다르다. M1은 2001년 이후 가용 경기 기록, 사건·선수 모델은 2023년 이후 자료를 활용한다. 인수 표준·검증·모델 자료의 실행 ID는 [자료 계보](../standards/execution_handover.md#data)에서 관리한다.

## 4. 핵심 예측 모델 개발

### 4.1 공통 개발 절차

1. 문제·입력·정답·평가 단위와 기본 비교 기준을 확정한다.
2. Train의 품질·분포·결측·희소성·시간적 이동을 분석하고 기준 모델을 만든다.
3. 동일 데이터·기간·지표에서 제한된 후보를 비교한다. 특징·모델·파라미터의 변경은 실제 개발 근거에 연결한다.
4. 모델 수·구조·지원·추론 비용·오차 및 보정 차이를 함께 기록한다. 검증 점수만 유리하게 보고하지 않는다.
5. 선택 모델을 버전·설정·Feature 계약·학습 소스·자료 지문·평가·대표 입력과 함께 저장한다.
6. 독립 프로세스로 재로딩·추론·기준 출력 비교, 오류·회귀 검증을 수행한다. 최종 Test는 이 선택 과정에 사용하지 않는다.

<a id="task-game-outcome"></a>

### 4.2 M1 경기 결과·득점

저장 프로필 분포 하나를 홈·원정에 사용하고 결합 분포에서 기대득점·스코어·승무패를 계산한다. 기준 빈도, 구간 프로필, 선택 포아송 후보를 동일 개발 조건에서 비교했다. 운영 모델의 선택과 사후 가정 시즌 전망을 구별한다. [M1 기술 계약](../standards/game_outcome_score.md).

### 6.4 원리에서 구현과 검증까지

수식은 구현을 설명하기 위해 사용한다. 강의 전사의 알고리즘, 저장 모델에서 확인되는 처리와 해당 처리의 실측 결과는 서로 다른 증거다. 아래 개발 수치는 기존 평가에서 인용하며, 2026년 고정 Test의 결과와 비교하려면 별도의 [최종 평가 계약](../standards/final_evaluation.md#evaluation)을 사용한다.

#### M1 경기 결과·득점 분포

- **원리 응용 — 반복 검증과 손실.** 강의의 교차검증은 여러 분할에서 일반화를 확인한다. M1은 경기 단위의 시간 방향을 유지하기 위해 2023·2024·2025년을 차례로 검증하며 매번 그 시즌 이전 자료로만 적합한다. `backtest.py`에서 720경기씩 2,160경기를 확인했다. 2025년 단일 Validation의 홈·원정 결과 빈도 기준과 다년 백테스트의 동점 보정 경험 분포 기준은 서로 다르므로 차이값을 합산할 수 없다.
- **프로젝트 확장 — 희소 분포와 결합의 정합성.** `model.py`는 팀과 상대의 시즌·최근 이력을 사용하고, 표본이 적은 프로필의 경험 득점 분포를 상위 기준에 수축한다. 홈·원정 PMF의 곱에 동점 여부별 가중치를 적용한 뒤 결합 확률을 정규화한다. 이때 동일한 결합표에서 홈 득점이 원정 득점보다 큰 셀, 같은 셀, 작은 셀의 질량 합이 각각 홈승·무승부·원정승 확률을 이루고, 주변분포가 기대득점의 근거가 된다. 기하 꼬리와 절단 상한은 드문 득점과 수치 절단을 다룬다. 동점 가중치 하나가 구장·날짜별 득점 상관 전부를 설명하지는 못한다.
- **실험과 운영 판단.** 2025년 720경기에서 득점 CRPS는 1.84664→1.82266, 승무패 Log loss는 0.81083→0.80047이었다. 무승부 평균 예측 확률 2.07%는 관측 비율 3.06%보다 낮았다. `poisson.py`의 비교 모델은 로그 연결과 L2 정규화 NLL을 사용했다. 시즌별 백테스트에서 운영 분포보다 MAE가 0.00077 낮았지만 CRPS가 0.06924, Log loss가 0.00459 높아 운영에는 경험 분포 방식을 유지했다. [M1 구현·검증 기록](../standards/game_outcome_score.md#lecture-methods)

#### M2 타석 결과

- **직접 적용 — 다항 로지스틱 회귀와 NLL.** 실제 타석 범주를 정답으로 하여 로그 확률의 음수를 최소화한다. 경사하강은 정답 범주에 배정한 확률을 높이는 방향으로 계수를 갱신한다. `model.py`와 `probability.py`가 특성, 확률 변환 및 후처리를 담당한다. 정확도와 Macro F1은 최빈 분류를, Log loss와 Brier는 확률 벡터를 평가한다.
- **프로젝트 확장 — 구조적 0과 시간순 보정.** 경기 상태에서 불가능한 결과를 마스킹하고 허용 범주에만 확률 질량을 배정한다. Train 사전분포 혼합은 허용되지만 드문 사건에 질량을 줄 수 있다. 2025년 전반기만으로 보정하고 후반기로 선정한다. 보정된 확률도 주어진 경기 규칙의 구조적 0을 보존해야 한다.
- **실험과 운영 판단.** 선정 표본 25,203타석에서 운영 `regularized_temperature_bias`의 Log loss·Brier는 1.66720433·0.74773852였다. 조건부 빈도 기준은 1.68872559·0.75401765였다. 온도만 쓴 후보는 $T=1$로 부모와 같은 결과라 개선 조건을 충족하지 못했다. 미보정 `logistic`의 Macro F1 0.06727129는 운영 후보의 0.05093328보다 높다. 운영 선택이 모든 클래스의 최빈 분류 개선을 의미하지 않는다. [M2 구현·검증 기록](../standards/plate_appearance.md#lecture-methods)

#### M3 선수 미래 성적

- **원리 응용 — 손실을 줄이는 분기.** 강의의 분류 트리는 엔트로피 감소로 분할을 비교한다. M3의 회귀 후보는 7일·28일·잔여 정규시즌의 관측 가능한 Count에 대한 제곱오차 감소를 사용한다. 깊이 2·4 및 잔차 축소율 0.25·0.50·1.00의 사전 후보로 복잡도를 비교했다. 운영 투수는 깊이 4의 공유 잔차 트리, 운영 타자는 과거 기록 기반 통계 후보였다. 각 역할을 저장 예측기 하나로 센다.
- **프로젝트 확장 — 관측 완료 마스크와 출력 투영.** 월요일 이전에 알려진 입력만 쓰고, 각 기록과 기간이 실제로 완료된 경우만 손실에 넣는다. 비음수 Count, 기간 간 순서, 분자·분모 일관성을 예측 후 제약으로 맞춘다. 2024년 시간순 잔차에서 얻은 구간 반경을 최종 Train 적합 모델에 전이한다. 90%는 목표 포함 수준이다. 동일 선수와 중첩 기간, 재적합으로 인해 90% 유한표본 보장을 주장할 근거는 없다.
- **실험과 운영 판단.** 개발에서는 같은 관측 마스크와 척도로 기준·직접 트리·잔차 트리·이력 후보를 비교했다. 2026년 고정 투수 Test에서 정규화 RMSE는 0.502286→0.494237로 낮아졌고 MAE는 0.323385→0.364164로 높아졌다. 기간별·기록별 분모와 오차를 함께 봐야 한다. 단일 공유 트리, 랜덤 포레스트의 복원 추출, 부스팅의 순차 앙상블은 각각 별개의 절차다. 랜덤 포레스트·부스팅·OOB는 이 기능에서 실행 증거가 없다. [M3 구현·검증 기록](../standards/player_performance.md#lecture-methods) · [2026년 평가](../standards/final_evaluation.md#evaluation)

#### M4 경기 상황 가치

- **직접 적용 — 이진 확률과 경사하강.** 같은 공격팀 관점으로 승리를 1, 패배와 무승부를 0으로 둔다. 선형 점수 $z$를 시그모이드로 변환해 $p$를 얻고, 이진 NLL의 로짓 기울기 $p-y$를 사용한다. `model.py`의 승리 로지스틱과 `value.py`의 타석 가치 계산은 책임이 다르다. L2는 비교 후보에서 검토했으며 운영 `logistic_core`의 L2는 0이다.
- **프로젝트 확장 — 조건부 기대득점과 상태 전이.** 잔여 기대득점은 과거 주자·아웃 상태에서의 조건부 평균을 사용한다. 희소하면 지원되는 조건으로 후퇴한다. 타석의 득점 가치는 해당 타석의 득점에 전후 잔여 기대득점의 차이를 더한다. WPA는 동일 공격팀의 전후 승리확률 변화다. LI는 가능한 상태 전이의 절대 WPA 기대량을 Train 기준으로 정규화하며 해당 타석의 실제 결과를 미리 쓰지 않는다.
- **실험과 운영 판단.** 2025년 동일 82,848상태에서 승리 Log loss는 빈도 0.4571에서 Core 0.4511로 낮아졌으며 ECE는 0.0117에서 0.0205로 높아졌다. 조건부 RE의 RMSE 0.9529는 전역 평균 1.0359보다 낮았다. LI 지원은 26,936/41,424 타석쌍이었다. ECE 악화와 LI 미지원은 정상 실행 여부와 독립적인 해석 제한이다. [M4 구현·검증 기록](../standards/game_state_value.md#lecture-methods)

#### M5 다음 투구

- **직접 적용 — 지도 다항 분류와 NLL.** 공 직전 상태로 구종·결과의 공동 클래스를 학습한다. `model.py`의 70개 공동 셀을 구종별 또는 결과별로 합해 각각 10개·7개 주변 확률을 낸다. 공동과 주변 지표를 나란히 보면 한 축의 악화를 공동 점수에서 놓치지 않는다.
- **프로젝트 확장 — 온도와 다중 지표 선정.** `development.py`는 2025년 보정과 후보 선정 구간을 분리하고, `0.99 * softmax(z/T) + 0.01 * p_train` 형태에서 유한 후보를 비교했다. T는 로짓의 스케일을 바꾸며 Train 사전 혼합은 계속 적용된다. 운영은 $T=1.15$다. 희소 L2 지연 감쇠와 계수 평균은 비교 후보 계열의 기능이었다. 계수 평균은 동일 학습 경로에서 얻은 파라미터의 평균이다. Soft Voting이 결합하는 단위는 각각의 모델이 출력한 확률이다.
- **실험과 운영 판단.** 2025년 전체 Validation에서 온도 적용 전후 공동 Brier는 0.91747048→0.91521472지만 구종 Brier는 0.67594927→0.67648026이었다. 선정의 1차 목적은 공동 확률 품질이다. 2026년 Test에서도 구종·결과·공동의 보정 지표와 희귀 구종 지원을 따로 보고한다. 위치 모형은 운영 범위 밖이다. [M5 구현·검증 기록](../standards/pitch_outcome.md#lecture-methods)

### 6.6 미적용·과제 요구의 처리

무작위 K-fold·Stratified K-fold 및 OOB는 시간과 같은 경기 묶음을 지키는 최종 검증을 대신하지 않는다. Bootstrap은 학습 표본 재추출이며 시즌 Monte Carlo와 다르다. 단일 모델의 계수 평균화를 독립 모델의 Soft Voting으로 집계하지 않는다. KNN·SVM·RF·Bagging·Boosting·Stacking·Grid/Random Search·GPU 등은 실제 비교·실행 근거가 없는 기능에서 미실험으로 표시한다. 선행의 실제 후보 실험과 현재 운영을 구별한다. 학습형 모델의 Bias–Variance를 설명하되 정량 분해나 독립 학습 곡선의 실측이 없는 항목은 미실행으로 기록한다. 깊이·L2·보정 후보별 오차는 실제 대조로 인용할 수 있다. 후보 비교표, 일반화 학습 곡선, 분산의 직접 추정은 요구하는 증거가 다르다.

과제 가이드 4쪽의 데이터 준비·문제 정의·EDA·Baseline·피처 엔지니어링·비교·최적화·결론에 실제 자료/모델/실행 산출물을 연결한다. 단순 규칙 계산 기능에 학습·튜닝이 없는 것은 문제의 책임을 분리한 결과다. 과제 전체의 요구 충족 여부는 최종 제출물에서 별도로 확인한다. 가이드 3쪽의 AI 활용 및 설명 가능성을 위해 실제 수행·검증·작성 보조를 구분한다. 확장 A(서비스화), B(LLM 결합)는 현 프로젝트 구현 범위 외다.

### 9.4 공통 문서 작성 및 검토 규격

문서는 GitHub Markdown으로 작성한다. H1 제목 아래 문서 역할·적용 범위·확인 기준일·저장소 경로·기준 소스·연관 작업·자료 이용 범위의 공통 표, 요약, 목차, 번호 본문 순으로 구성한다. 한국어 설명에는 원래 기술 식별자와 실행 문법을 보존한다. 집계 표에는 역할과 근거가 다른 지표의 분모와 단위를 명시한다. 명시적인 영어 앵커와 번호가 있는 목차를 사용한다. 기존 연결 앵커는 가능한 한 보존한다. 긴 파일은 역할에 맞게 절을 분리하되 중복 상세 계산은 정본에 연결한다.

기술 문서의 기본 10절은 ① 목적·지원 범위, ② 자료·분할·품질, ③ 입력·전처리, ④ 정답·출력, ⑤ 모델·방법, ⑥ 강의 원리와 확장, ⑦ 평가·실제 결과, ⑧ 구현·산출물·재현성, ⑨ 검증·한계·후속 연결, ⑩ 실행 명령이다. README·개발 흐름·공통 계약처럼 역할이 다른 문서는 같은 시각 체계에서 필요한 절을 추가/조정한다. 강의 적용 표는 출처·구분·실제 구현·검증 및 한계를 함께 기록한다. 상세 실험 수치·실패와 미적용의 이유를 읽기 쉽게 축약한다는 명목으로 제거하지 않는다.

공통 표의 열은 항목/정의 또는 근거/결과/한계로 일관시킨다. 날짜·기간의 포함/제외 경계·단위·분모·버전·파일명 대소문자를 명시한다. 명령은 코드 펜스의 언어를 지정하고 실제 경로와 인자, 예상 종료값 및 생성/읽기 전용 여부를 밝힌다. 불변 자산·과거 실행에 연결하는 링크는 기록된 Commit/ID를 사용한다. 새 Issue의 제목·공유 문서에는 실제 작업명을 쓰며 내부 작업 흐름 코드를 노출하지 않는다.

강의 항목은 직접 적용, 원리 응용, 강의 전사 확인 범위 밖의 프로젝트 확장, 비교 실험 후 미채택, 미적용을 구별한다. 기능별 표에는 원리, 구현에서의 역할, 검증 증거와 실패·해석 경계를 남긴다. 과제 가이드의 수행 요구는 실제 실행 결과와 별도로 표시한다.

문서는 실제 코드와 사용자 검증에 기반한다. 기존 설명과 현재 상태가 충돌할 때에는 당시 기록과 현재 확인 사실을 구분한다. 관련 자료를 열지 못했다면 직접 확인으로 기록하지 않는다. [공통 계약](../standards/project_contract.md)의 규칙과 일치해야 한다.
