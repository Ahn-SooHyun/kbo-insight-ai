### 1.2 개발 순서의 예외와 변경 통제

데이터 누락이나 원천 기록 충돌이 발견되면 임의 수동 정정 대신 자동 확인의 가능성과 품질 조건을 검토한다. 새로운 자료나 주 예측기, 배포·LLM 결합, 신규 규칙 적용은 별도 범위다. 한 작업에서 발생한 발견이 다음 작업을 변경할 필요가 있으면 의존성·원인·영향·완료 기준을 먼저 확정한다. 이미 공개된 Test를 보고 선정 기준을 변경하지 않는다.

### 1.3 공통 기준의 관리 위치

[공통 계약](../standards/project_contract.md)은 시점·정답·기능·모델 수·평가 원칙을 정의한다. 개별 모델의 실제 입력·알고리즘·파라미터·실험·오류·명령은 기능별 실행 계약에 남긴다. README는 사용자 진입점, [실행 인수](../standards/execution_handover.md)는 실제 환경과 저장 자산의 연결 책임을 가진다.

## 2. 설계·개발 기반 준비

<a id="task-prediction-contract"></a>

### 2.1 예측·평가 기준 고정

모델마다 표본 단위, 입력 시점, 미래 예측 대상, 정답 종료와 유효 분모를 먼저 정한다. 관측되지 않은 자료를 실제 0으로 가정하지 않는다. 원본에서 구별 가능한 세부 결과만 범주화한다. 공통 규칙의 변경은 영향 받는 자료·모델·평가·시즌·설명 계약에 연결한다.

<a id="task-development-foundation"></a>

### 2.2 최소 개발 기반

Python 3.12.15, uv 0.13.7, `.python-version`, `pyproject.toml`, `uv.lock`, `kbo.toml`을 기준으로 한다. 사용자 실행은 같은 가상환경의 Python을 명시한다. 설정·소스·테스트·문서와 생성 데이터/모델/결과는 경로 책임을 구분한다. Secret은 추적하지 않는다. 최소한의 표준 라이브러리 기반 모듈을 유지하고 데이터 검사에서 필요한 선택 의존성만 사용한다. GPU는 실질적 이득과 지원 근거가 있을 때만 추가한다. Notebook은 핵심 로직의 정본이 아니라 EDA와 실험·시각화에 사용한다.

완료 근거: 실제 두 CLI 진입점, 도움말·`check`, 설정 정상/오류 경계, 잠금 설치, 읽기 전용 동작, 테스트 로그와 결과 파일. [README 설치·실행](../../README.md#commands).

## 3. 자동 수집·데이터 구축

<a id="task-source-pilot"></a>

### 3.1 소규모 원천 확인과 조건부 판정

승인된 자동 수집 원천의 실제 바이트·필드·식별자·이벤트 순서·파일 형식·자료 이용 권한을 점검한다. Naver 표본과 고정 HF 배포 파일의 응답 제한·타입·구조·원본 재열람을 구분한다. 통신 성공은 의미 검증을 뜻하지 않으며, 표본의 필드 존재는 전체 자료의 완전성을 뜻하지 않는다. 라인업 발표 시각, 교체, 도루·견제·번트의 자동 식별 가능성을 항목별로 기록한다.

<a id="task-source-collection"></a>

### 3.2 전체 확보와 원본 보존

명세는 대상·판본·출처·조건을 고정한다. 재시도·timeout·응답 제한·실패와 보류를 기록한다. 저장 객체는 SHA-256으로 판별하고 기존 파일을 수정하지 않는다. 중단 뒤 재개는 이미 확보한 객체의 검증과 미완료 목록에 근거한다. 수집·갱신과 단순 보고는 별개 명령이다. 인수 원본 46개, 논리 대상 48개, 판본 50개는 실제 확인 기록의 범위다.

<a id="task-standardization"></a>

### 3.3 표준화·품질·집계 대조

raw → interim → processed의 변환 이력을 보존한다. 컬럼·타입·Null·범위·중복·식별자·날짜·경기·타석·투구 관계와 경기/선수별 집계를 확인한다. Raw와 기존 표준판은 수정하지 않는다. 보완 표준판에는 포스트시즌 유효 결과 46경기 및 정규시즌 종료 근거를 연결했다. #40에서 동일 입력으로 신규 보완판과 기존 DB 물리 해시 일치를 확인했다. 이 검증은 공식 모든 경기 기록의 사실 인증이 아니다.

<a id="task-model-data"></a>

### 3.4 모델 입력·정답·시간 분할

모델별 논리 표본을 만들고 같은 경기의 하위 기록을 중복·교차 분할하지 않는다. M3는 월요일 기준의 모든 과거 입력과 미래 기간 정답을 분리한다. 학습 시점에 관측이 완료된 정답만 사용하며 기간 중 실제 0과 미관측, 미완료, 0 분모를 구별한다. 입력·정답 허용 열, 감사 열, 데이터 분할·제외는 명세 및 검증 결과에 남긴다. Train EDA는 Train 기준의 특성·지원·누락·기준 통계에 사용한다.

| 구간       | 기간(논리 시각 KST)             | 역할                             |
| ---------- | ------------------------------- | -------------------------------- |
| Train      | 2025-01-01 이전                 | 기준·학습·학습형 전처리          |
| Validation | 2025년                          | 개발 비교·선정, 모델별 보정 분리 |
| 최종 Test  | 2026-01-01 이상 2026-11-26 미만 | 고정 모델 독립 평가만            |

자료 범위와 실제 완료 정답은 모델별로 다르다. M1은 2001년 이후 가용 경기 기록, 사건·선수 모델은 2023년 이후 자료를 활용한다. 인수 표준·검증·모델 자료의 실행 ID는 [자료 계보](../standards/execution_handover.md#data)에서 관리한다.

## 4. 핵심 예측 모델 개발

### 4.1 공통 개발 절차

1. 문제·입력·정답·평가 단위와 기본 비교 기준을 확정한다.
2. Train의 품질·분포·결측·희소성·시간적 이동을 분석하고 기준 모델을 만든다.
3. 동일 데이터·기간·지표에서 제한된 후보를 비교한다. 특징·모델·파라미터의 변경은 실제 개발 근거에 연결한다.
4. 모델 수·구조·지원·추론 비용·오차 및 보정 차이를 함께 기록한다. 검증 점수만 유리하게 보고하지 않는다.
5. 선택 모델을 버전·설정·Feature 계약·학습 소스·자료 지문·평가·대표 입력과 함께 저장한다.
6. 독립 프로세스로 재로딩·추론·기준 출력 비교, 오류·회귀 검증을 수행한다. 최종 Test는 이 선택 과정에 사용하지 않는다.

<a id="task-game-outcome"></a>

### 4.2 M1 경기 결과·득점

저장 프로필 분포 하나를 홈·원정에 사용하고 결합 분포에서 기대득점·스코어·승무패를 계산한다. 기준 빈도, 구간 프로필, 선택 포아송 후보를 동일 개발 조건에서 비교했다. 운영 모델의 선택과 사후 가정 시즌 전망을 구별한다. [M1 기술 계약](../standards/game_outcome_score.md).

### 6.4 미적용·과제 요구의 처리

무작위 K-fold·Stratified K-fold 및 OOB는 시간과 같은 경기 묶음을 지키는 최종 검증을 대신하지 않는다. Bootstrap은 학습 표본 재추출이며 시즌 Monte Carlo와 다르다. 단일 모델의 계수 평균화를 독립 모델의 Soft Voting으로 집계하지 않는다. KNN·SVM·RF·Bagging·Boosting·Stacking·Grid/Random Search·GPU 등은 실제 비교·실행 근거가 없는 기능에서 미실험으로 표시한다. 선행의 실제 후보 실험과 현재 운영을 구별한다. 학습형 모델의 Bias–Variance를 설명하되 정량 분해·학습 곡선을 수행하지 않았다면 완료로 쓰지 않는다.

과제 가이드 4쪽의 데이터 준비·문제 정의·EDA·Baseline·피처 엔지니어링·비교·최적화·결론에 실제 자료/모델/실행 산출물을 연결한다. 단순 규칙 계산 기능에 학습·튜닝이 없는 것은 문제의 책임을 분리한 결과다. 과제 전체의 요구 충족 여부는 최종 제출물에서 별도로 확인한다. 가이드 3쪽의 AI 활용 및 설명 가능성을 위해 실제 수행·검증·작성 보조를 구분한다. 확장 A(서비스화), B(LLM 결합)는 현 프로젝트 구현 범위 외다.

## 7. 종합 검증·설명

<a id="task-final-evaluation"></a>

### 7.1 고정 설정 최종 평가

Train 이전 통계·운영 예측기·평가 정책을 고정하고 2026-01-01 이상 2026-11-26 미만의 적격 정규시즌 Test를 평가한다. 명세에 입력과 코드·문서·환경·정답 계약 및 지표를 기록한다. 입력 열 제한과 읽기 전용 Authorizer로 정답 접근을 차단한다. 기존 모델을 재학습하지 않고 저장 추론 뒤 정답 키를 연결한다. [고정 최종 평가](../standards/final_evaluation.md)에서 실제 결과와 악화를 함께 보고한다.

### 7.2 시즌 검산

동일 Seed·반복 조건, 증가한 반복의 앞부분 일치, 확정 경기 보존, 순위·부모 시드·시리즈·공동 유효 분모·팀 기록·일정 난이도를 다시 계산한다. 원천 기록 충돌을 정상 처리로 은폐하지 않는다. 2025 가정과 2026 미지원은 유지한다. [시즌 검산](../standards/season_forecast_validation.md).

### 7.3 예측 설명·실패 사례

선형 로짓의 Train 평균 기반 독립 개입 SHAP, 비선형 모델의 실제 계산 단계·트리 경로 및 확률/상태 변환을 정확히 구별한다. 전역 설명과 실패 사례 표본, 전체 모집단 진단과 개별 저장 행을 분리한다. 저장 운영 예측과 복원값을 비교한다. SHAP과 실제 결과의 차이를 인과효과로 설명하지 않는다. [예측 설명](../standards/prediction_explanation.md).

### 8.1 재실행과 사용자 인수

같은 Windows 11 AMD64 장비의 별도 작업 사본에서 CPython 3.12.15, uv 0.13.7, PyArrow 26.0.1, SQLite 3.53.1, 프로젝트 0.1.0 환경을 신규 구축했다. 잠금 설치, 의존성 확인, 설치 EXE·모듈 진입점, 외부 CWD, 명시 루트 및 없는 루트 Exit 2를 확인했다. 모델 재학습과 원본 재수집은 수행하지 않았다.

| 검증           | #40의 결과                                           | 증거 한계                                  |
| -------------- | ---------------------------------------------------- | ------------------------------------------ |
| 보완 표준 DB   | 새 실행과 기존 DB SHA-256 일치                       | 신규 모델 자료 DB 생성 아님                |

| 회귀·보존      | 734/734, 보호 파일 458개 변경·추가·삭제 0            | 지정 파일 및 실행 환경의 확인 범위         |

### 8.2 문서 적용 후 검증

상대 경로·대소문자·명시 앵커·CLI 옵션과 전역 인자 위치를 확인한다. README에서 저장 자산과 대표 예측·결과까지 이어지는 사용 경로를 검증한다. #40 회귀를 선행 근거로 인수하되 이번 문서 변경이 영향을 주는 검사 및 실제 명령은 별도 로그를 남긴다. 신규 학습이나 평가 전량 재추론은 문서 수정의 자동 조건이 아니다. 작업 트리·변경 파일·공백 검사·사용자 실제 실행을 확인한다. 기존 인수 근거와 신규 확인을 섞지 않는다.

## 9. 증거·실패·문서 관리

### 9.1 증거 등급과 상태 표현

| 구분                | 기록                                                |
| ------------------- | --------------------------------------------------- |
| 코드/문서 직접 확인 | 실제 판본, 경로, 인터페이스, 근거                   |
| 사용자 실행         | 실행 명령·실제 종료 코드·환경·출력·파일 지문        |
| 저장 자산 직접 대조 | 파일·DB·manifest·비교 대상과 방법                   |
| 개발/기술 수용      | 요구사항·TODO별 판정과 조건                         |
| Git/GitHub 상태     | Commit·Push·PR·리뷰·Merge·Issue 종료 각각 실제 근거 |
| 미확인·추정         | 이유·영향·추가 증거, 성공으로 표기 금지             |

### 9.2 최소 증거 묶음

실제 Issue 및 변경 범위, 소스 기준, 변경 파일, 실행 환경, 입력/모델/결과 ID, 명령, 정상/오류 종료값, 테스트 및 회귀, 실패·제한, Git 상태를 기록한다. 고정 명세의 소스·문서·환경·자산 지문은 현재 설명 문서와 분리한다. 실패·악화·누락·부분 완료는 제거하지 않는다.

### 9.3 실패와 회귀 확인

실패는 원인과 영향 범위를 분석하고 같은 입력의 수정 전후 또는 별도 회귀를 검증한다. 포착한 오류만 보완하고 다른 사용자 변경을 보존한다. 계산 검증과 문서 링크 검사, 전체 성공을 구분한다. 내용 주소 지문은 무결성의 한 근거이지 사실 정확성·성능·안전성의 증명은 아니다.

<a id="documentation-standard"></a>

### 9.4 공통 문서 작성 및 검토 규격

문서 형식은 GitHub Markdown이며 한국어 설명과 기술 식별자·수학·코드 원문을 사용한다. 장식적 이모지·뱃지보다 정보의 정확성과 세밀함을 우선한다. 제목 아래 역할·적용 범위·KST 확인일·저장 경로·소스 기준·실제 Issue·자료 이용 범위의 메타데이터 표를 둔다. 명시적인 영어 앵커와 번호가 있는 목차를 사용한다. 기존 연결 앵커는 가능한 한 보존한다. 긴 파일은 역할에 맞게 절을 분리하되 중복 상세 계산은 정본에 연결한다.

기술 문서의 기본 10절은 ① 목적·지원 범위, ② 자료·분할·품질, ③ 입력·전처리, ④ 정답·출력, ⑤ 모델·방법, ⑥ 강의 원리와 확장, ⑦ 평가·실제 결과, ⑧ 구현·산출물·재현성, ⑨ 검증·한계·후속 연결, ⑩ 실행 명령이다. README·개발 흐름·공통 계약처럼 역할이 다른 문서는 같은 시각 체계에서 필요한 절을 추가/조정한다. 강의 적용 표는 출처·구분·실제 구현·검증 및 한계를 함께 기록한다. 상세 실험 수치·실패와 미적용의 이유를 읽기 쉽게 축약한다는 명목으로 제거하지 않는다.

공통 표의 열은 항목/정의 또는 근거/결과/한계로 일관시킨다. 날짜·기간의 포함/제외 경계·단위·분모·버전·파일명 대소문자를 명시한다. 명령은 코드 펜스의 언어를 지정하고 실제 경로와 인자, 예상 종료값 및 생성/읽기 전용 여부를 밝힌다. 불변 자산·과거 실행에 연결하는 링크는 기록된 Commit/ID를 사용한다. 새 Issue의 제목·공유 문서에는 실제 작업명을 쓰며 내부 작업 흐름 코드를 노출하지 않는다.

문서는 실제 코드와 사용자 검증에 기반한다. 기존 설명과 현재 상태가 충돌할 때에는 당시 기록과 현재 확인 사실을 구분한다. 관련 자료를 열지 못했다면 직접 확인으로 기록하지 않는다. [공통 계약](../standards/project_contract.md)의 규칙과 일치해야 한다.
